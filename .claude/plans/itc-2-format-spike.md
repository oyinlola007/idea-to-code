# Feature: ITC-2 plan file format spike

The following plan should be complete, but it's important that you validate documentation and task sanity before you start implementing. This is a **spike**: the code is spike-quality (typed, tested where it counts, not polished), but the **fixtures, schema decisions and results doc are kept** and feed ITC-4.

## Feature Description

Prove that the plan file format (YAML in `plan/`, flows you can drill into, components, connectors with data) can be **written by hand, generated by LLMs through operation tools, edited by an outside coding agent from GUIDE.md alone, and laid out readably by ELK**, before any product code depends on it. The output is a decision recorded in `docs/spikes/format.md`: keep, flatten or simplify the format, plus the layout direction per flow and the models marked "tested".

## User Story

As the founder building idea-to-code
I want evidence that the plan format works for people, for LLMs and for layout
So that I lock in the hardest-to-undo decision (the file format) knowing it works, instead of guessing.

## Problem Statement

Once maps exist in users' folders, the format can only change by adding things (no format version in user files). If the format is hard for LLMs to produce validly, confusing for outside agents, or lays out badly, every later ticket inherits that problem.

## Solution Statement

A self-contained TypeScript spike in `spikes/format/` with:
1. a v0 zod schema and a validator that checks rules across files;
2. a minimal set of comment-preserving operations on YAML documents;
3. hand-written career-app fixtures;
4. a **built-in agent harness** (Vercel AI SDK, operations as tools, the real context shape) run against several models;
5. a **Claude Code harness** (headless `claude -p`, given only GUIDE.md and the skill file);
6. an ELK layout renderer producing an HTML page for the founder to judge.

Results go into `docs/spikes/format.md`.

### Patterns to Follow

There's no existing code. Conventions to establish, which ITC-4 will keep:
- **Naming:** files in `kebab-case.ts`; types in `PascalCase`; functions in `camelCase`. Plan IDs are kebab-case slugs.
- **Pure core:** `schema`, `validate`, `ids`, `ops` and `outline` take and return data (file contents or `yaml.Document` objects). Only `load.ts`, the CLI and the harnesses touch the filesystem.
- **Errors:** validator issues are data (`{ file, line, col, severity: 'error' | 'warning', code, message }`), never thrown. Operations return `{ ok: true, changedFiles, created? } | { ok: false, error: string }`, with error strings written so an LLM can act on them, e.g. `"Node 'tailr-cv' not found in flow 'main'. Existing nodes: search-jobs, good-fit, tailor-cv"`.
- **ESM only** (`"type": "module"`), and strict TS.

## FORMAT v0 (decided in this plan; the spike tests it)

**`plan/map.yaml`** holds the overview. Feature nodes are implied by `features`, connectors by `connections`. Optional shared `components` are for system design at the top level.

```yaml
project: Career Manager
description: Open-source app to manage a career end to end.
features:                      # order = overview order
  - id: career-profile
    label: Career profile and job overview
    description: …
  - id: job-search
    label: Job search and tailored applications
components:                    # optional, shared across features
  - id: app-database
    kind: database
    tech: PostgreSQL
    label: App database
connections:                   # edges in the overview: "flows into"
  - { from: job-search, to: application-tracker, data: application record }
  - { from: email-integration, to: application-tracker, data: status update from email }
```

**`plan/features/<feature-id>.yaml`**: the filename must equal `feature`, which must appear in `map.yaml`.

```yaml
feature: job-search
flows:
  main:                        # required: the feature's top-level flow
    label: Job search
    nodes:
      - { id: search-jobs, type: step, label: Search jobs, status: done }
      - { id: good-fit, type: decision, label: Good fit? }
      - id: tailor-cv
        type: step
        label: Tailor CV
        description: Generate a CV tailored to the job description.
        status: in_progress
        expands: tailor-cv-flow
      - { id: llm-api, type: component, kind: external-api, tech: Claude API, label: LLM API }
    edges:
      - { from: search-jobs, to: good-fit }
      - { from: good-fit, to: tailor-cv, label: "yes" }
      - { from: tailor-cv, to: llm-api, data: job description + profile }
  tailor-cv-flow:
    label: Tailor CV
    nodes: [ … ]
    edges: [ … ]
```

**Rules (the validator enforces all of them):**
1. **Every `id` is unique across the whole plan**: features, components, flows and nodes share one namespace. This is a single rule that's easy for agents to follow, and `reference` targets stay unambiguous. Slugs match `^[a-z0-9]+(-[a-z0-9]+)*$`.
2. **Node `type`** is one of: `start`, `end`, `step`, `decision`, `component`, `reference`.
   - `component` needs `kind` (an open string) and may have `tech`.
   - `reference` needs `ref` (a flow ID anywhere).
   - Only `step` and `component` may have `status` (`todo` | `in_progress` | `done`; leaving it out means `todo`) or `expands`.
3. **`expands`** must point to a flow **in the same file**. Each non-`main` flow must be expanded by **exactly one** node. `main` can't be expanded. A flow nobody expands is a warning (`orphan-flow`). Being expanded twice is an error, and the fix is `reference`.
4. **There are no cycles.** This follows from rule 3, but check it explicitly anyway, to give a clear message.
5. **Edges:**
   - `from` and `to` must be nodes in the **same flow**.
   - No duplicate `(from, to)` pairs, and no self-loops.
   - An edge leaving a `decision` should have a `label` (warning if it doesn't).
6. **Overview connections:** `from` and `to` must be feature or top-level component IDs.
7. **A feature listed in `map.yaml` with no file** is a warning (`feature-without-flows`), so partly written plans are valid. **A file with no `map.yaml` entry** is an error.
8. **Unknown keys** are errors in v0. Strict mode catches agent typos; this is revisited in the decision, since additive evolution may need it relaxed.

## NOTES

- **Why the overview is `features` + `connections` and not a generic flow:**
  - Overview nodes always map to feature files, so a separate node list would duplicate IDs and invite drift.
  - Components at the top level cover system design across features.
  - It's still additive later: entry/exit points on connections can be added without breaking maps.
- **Why one ID namespace:** agents make fewer mistakes with one rule ("every id is unique") than with scoped rules, and `reference`, comments and history stay unambiguous. The cost is longer slugs in big plans, which is acceptable.
- **Why the Claude Code route edits files directly (no MCP):** this is the worst case, and the baseline. If agents can do it from GUIDE.md alone, MCP (ITC-18) only makes it better.
- **What "valid after retries" means:** for the built-in route, the final project state passes the validator (tool errors along the way count as retries). For Claude Code, there are no retries: the final files must be valid.
- **Cost:** Claude Code is 9 short runs on the subscription. The built-in route is about 40 runs; each is ~5–15k input tokens × ~10–30 steps, a few dollars in total across models. Check `costUsd` from the Claude JSON output.
